## 背景与目标

现网匹配只在单服内进行，跨服房间靠人工开房，晚高峰排队 3-8 分钟。本次上线跨服匹配池，
并配合限时折扣券做拉活。

- 目标 1：晚高峰平均排队 ≤ 90 秒（当前 180 秒）；
- 目标 2：跨服房间分配失败率 ≤ 0.5%；
- 目标 3：折扣券核销率 ≥ 60%，且不产生负毛利订单。

## 范围

- 匹配服新增跨服匹配池与状态机（排队 → 分配 → 入场 → 结算）；
- 新增跨服房间服（Room Service）分配/释放接口；
- 商城服新增限时折扣券领取与支付回调核销；
- 网关透传新的匹配/商城接口，鉴权沿用现有登录态。

非目标：不做观战、不做跨区排行榜、不改动战斗结算公式。

## 玩法与业务规则

1. 排队超 120 秒，匹配池逐步放宽 ±200 分；超 300 秒仍未匹配则返回 `MATCH_TIMEOUT` 并退还次数。
2. 同一玩家同一时刻只能在一个匹配队列；重复 `enter` 必须幂等返回第一次的 `ticket_id`。
3. 房间分配成功后才扣"匹配次数"；分配失败必须回滚次数（同一事务）。
4. 折扣券每人每日限领 2 张，券与订单一一绑定；支付回调必须验签 + 订单幂等。
5. 券后价低于成本价时拒绝下单（`PRICE_BELOW_COST`），不允许负毛利。

## 接口契约

| 接口ID | 调用方 → 被调方 | 方法 | 路径 | 鉴权 | 幂等键 | 错误码 |
| --- | --- | --- | --- | --- | --- | --- |
| M-01 | 客户端 → 网关 → 匹配服 | POST | /v1/match/enter | 是 | request_id | MATCH_BUSY / ALREADY_QUEUED |
| M-02 | 客户端 → 网关 → 匹配服 | GET | /v1/match/state | 是 | — | TICKET_NOT_FOUND |
| M-03 | 客户端 → 网关 → 匹配服 | POST | /v1/match/cancel | 是 | request_id | TICKET_NOT_FOUND |
| M-04 | 匹配服 → 跨服房间服 | POST | /v1/cross/room/allocate | 是（内网 mTLS） | match_id | ROOM_EXHAUSTED / TIMEOUT |
| M-05 | 跨服房间服 → 匹配服 | POST | /v1/cross/room/release | 是（内网 mTLS） | room_id | ROOM_NOT_FOUND |
| S-01 | 客户端 → 网关 → 商城服 | POST | /v1/shop/discount/claim | 是 | request_id | LIMIT_EXCEEDED |
| S-02 | 客户端 → 网关 → 商城服 | GET | /v1/shop/discount/list | 是 | — | — |
| S-03 | 支付平台 → 商城服（回调） | POST | /v1/pay/order/callback | 是（签名验签） | order_id | SIGN_INVALID / ORDER_DUP |

约定：

- 鉴权：客户端接口用登录态 token；内部接口用 mTLS + 服务名；支付回调用平台公钥验签。
- 幂等：所有写接口必须带幂等键（`request_id` / `match_id` / `order_id`），服务端落去重表，TTL 24h。
- 超时与重试：客户端 3s 超时、同 `request_id` 可重试 2 次；内部 RPC 1s 超时、指数退避 3 次。
- 版本兼容：只允许新增可选字段；删除/改义字段必须标 `deprecated` 并保留两个版本周期。
- 字段级 schema、示例报文、错误码枚举见 `proto/match_v3.json` 与 `proto/shop_v2.json`。

## 数据与存储

- 新表 `match_ticket`（player_id, ticket_id, state, mmr, created_at）、`match_dedup`（request_id 唯一索引, ttl）；
- 新表 `coupon_order`（order_id, player_id, coupon_id, price, status）；
- 迁移要求：按版本号顺序、事务包裹、先加列后回填、不删除旧列；每步可回滚。

## 性能与容量

- 晚高峰 CCU 目标 5200，匹配服单实例容量 5000 → 需 2 实例 + 一致性哈希分池；
- 匹配循环 tick 预算 50ms，p99 ≤ 40ms；房间分配 QPS 峰值 800；
- 商城回调 QPS 峰值 200，允许 5s 内最终一致。

## 风控与安全

- 越权：封禁/发券等管理接口必须鉴权 + 权限位校验；
- 刷券：设备指纹 + 每日限领 + 去重表；异常领取率 > 5% 触发风控工单；
- 支付重放：`order_id` 唯一 + 验签 + 金额与订单核对；
- 经济：券补贴每日上限、券后价 ≥ 成本价、通胀日增幅 ≤ 0.5%。

## 灰度、回滚与监控

- 灰度：按服务器分组 5% → 20% → 全量，每档观察 30 分钟；
- 回滚：保留上一版本镜像 + `ops/rollback.sh`（反向执行本次迁移），回滚演练必须在灰度前完成；
- 监控：排队时长 P50/P99、分配失败率、券核销率、支付回调失败率、负毛利订单数（应为 0）。

## 验收标准

- 跨服匹配排队 P99 ≤ 90 秒，失败率 ≤ 0.5%
- 重复 enter/cancel/claim 请求必须幂等，不重复扣次数、不重复发券
- 匹配次数扣减与房间分配在同一事务，失败必须回滚
- 支付回调验签失败必须拒绝，重复回调不得重复发货
- 所有客户端接口必须鉴权，管理接口必须有权限位
- 迁移可按版本顺序执行与回滚，无破坏性变更

## 模块拆分

- 匹配服跨服池：`server/match.py`、`server/router.py`
- 跨服房间接口：`server/cross_room.py`
- 商城折扣券与支付回调：`server/shop.py`、`server/pay_callback.py`
- 迁移与配置：`migrations/`、`config/`
- 运维与回滚：`ops/rollback.sh`

## 排期与风险

- 服务端开发 5 人日，联调 2 人日，压测 1 人日，灰度 1 天；
- 风险 1：跨服房间服容量不足 → 提前扩容并设 `ROOM_EXHAUSTED` 降级到单服匹配；
- 风险 2：支付回调乱序 → 以 `order_id` + 状态机兜底，禁止状态回退；
- 未决项：跨服观战、跨区排行榜（本期不做，接口不预留）。
