# 游戏服务端开发报告：模板与接口归属

这份文档回答两个问题：**一份"特经典"的开发报告长什么样**，以及**接口到底谁定**。
可直接照抄 [`examples/game_server/fixture/ticket_classic.md`](../examples/game_server/fixture/ticket_classic.md)
（跨服匹配 + 商城折扣券的填好版本）。

---

## 1. 接口谁定：三方联审，协议 owner 维护

| 角色 | 在接口上的职责 | 不该做的事 |
| --- | --- | --- |
| 需求方（玩法/商业化策划） | 提出"要什么能力、什么时序、什么错误分支、验收指标" | 直接改字段类型/路径 |
| 客户端主程 | 确认客户端能实现的请求/响应、错误码、弱网重试 | 单方面定服务端内部接口 |
| 服务端主程（协议 owner） | 定字段级 schema、鉴权/幂等/超时、版本兼容策略，维护 `proto/*.json` | 私自改已冻结契约（要走变更评审） |
| QA / 运维 | 确认可测性、灰度/回滚、容量与监控指标 | 上线后才补验收口径 |

结论：**接口不是"服务端开发自己定"，也不是"客户端定"，是需求方 + 双端主程在技术评审上定稿，
服务端主程作为协议 owner 落成协议文件。** 开发报告里出现的是"契约意图"（谁调谁、方法/路径、
鉴权、幂等、错误码），字段级定义在协议文件里，避免两份真相。

## 2. 开发报告里的接口：该有，但分层

- **必须有**：接口清单（含调用方/被调方）、鉴权要求、幂等键、错误码、超时重试、版本兼容策略；
- **不应该有**：完整字段级 schema、几百行示例报文（放协议文件，报告只写版本号 + 本次变更点）；
- **两边服务器接口**：客户端↔网关↔游戏服、游戏服↔跨服房间服、游戏服↔支付平台，都要列进同一张表，
  只是"鉴权"列写各自的机制（登录态 / mTLS / 签名验签）。

在框架里三者是分开对照的：

```
开发报告接口表（report）  ← 需求侧声明的意图
        │
设计文档接口表（doc）     ← 玩法与规则的解释
        │
协议文件 proto/*.json     ← 冻结的契约（优先级最高）
        │
代码路由注册（code）       ← 实现
```

审计官（`auditor/code`）把四者合并成"声明清单"，再和代码对照：

- 声明了、代码没有 → `endpoint_missing`；
- 代码有、声明没有 → `endpoint_undeclared`；
- 声明要鉴权、代码没鉴权 → `auth_missing`；
- 声明废弃、代码还在服务 → `deprecated_still_served`。

所以"接口在开发报告里有没有"的答案是：**报告里有接口清单和约束，字段级以协议文件为准；
两者都会被审计当作依据。**

## 3. 模板（照这个填）

```markdown
# 开发报告：<功能名>（<单号>）

| 项 | 内容 |
| --- | --- |
| 报告单号 / 版本 | GS-YYYY-NNNN / v1.x（评审稿，日期冻结接口） |
| 需求方 / 技术负责人 | 策划 / 服务端主程（协议 owner） |
| 联审 | 客户端主程 / QA / 运维 |
| 目标版本 / 灰度 | 1.x.0，5% → 20% → 全量 |
| 关联文档 | proto/*.json、docs/design.md |

> 接口归属：本报告声明接口意图；字段级定义以 proto 为准，冲突时以协议为准。

## 背景与目标
（现状、痛点、可量化目标）

## 范围
（做什么；非目标：明确不做什么）

## 玩法与业务规则
（状态机、数值、边界、失败分支、回滚条件）

## 接口契约
| 接口ID | 调用方 → 被调方 | 方法 | 路径 | 鉴权 | 幂等键 | 错误码 |
|---|---|---|---|---|---|---|
| M-01 | 客户端 → 网关 → 匹配服 | POST | /v1/match/enter | 是 | request_id | MATCH_BUSY |

约定：鉴权机制、幂等 TTL、超时重试、版本兼容、字段级定义位置。

## 数据与存储
（新表/改表、迁移顺序、事务、可回滚）

## 性能与容量
（CCU、tick 预算、QPS、延迟目标）

## 风控与安全
（越权、刷奖、支付重放、经济上限）

## 灰度、回滚与监控
（分组比例、回滚脚本与演练、核心指标）

## 验收标准
- 可测的条目，一条一个断言（审计会检查它们在设计文档里有没有依据）

## 模块拆分
- 分片名：涉及文件（框架按这个并行派活）

## 排期与风险
（人日、依赖、风险与降级方案、未决项）
```

## 4. 评审检查清单（提测前逐条过）

- [ ] 每个接口都有调用方/被调方，内部接口写了鉴权机制（mTLS / 服务名 / 签名）；
- [ ] 所有写接口都有幂等键，且说明了去重存储与 TTL；
- [ ] 错误码覆盖并发、超时、越权、重放、额度不足；
- [ ] 字段级 schema 已进协议文件，报告只引用版本号；
- [ ] 迁移可按版本顺序执行与回滚，无 `DROP`/`NOT NULL` 无默认值；
- [ ] 容量数字（CCU、tick、QPS）与压测结论一致；
- [ ] 灰度比例与回滚脚本已演练；
- [ ] 验收标准每条都能在文档里找到依据（否则审计报 `acceptance_uncovered`）。

## 5. 和流水线的关系

`producer/intake` 解析这份报告：标题/范围/验收项/模块/接口表 → 工单；`plan` 拆成
`workstreams` 并行派给 `dev`；`auditor/code` 把报告接口表（source=`report`）、文档接口表
（`doc`）、协议文件（`spec`）合并后与代码对照；`server_risk/gate` 再叠加容量/回放/回滚/经济。
报告写得越像上面这份，后面审计能对上的就越多；写得含糊，审计会明确报"缺依据"，不会猜。
